# Financial Lens 实时财经新闻流设计

日期：2026-09-14  
状态：已确认，待实施计划

## 1. 背景与目标

当前首页新闻来自 `src/data/demoData.ts`，不会随现有行情和宏观数据任务一起更新。现有 GitHub Actions 只生成全球态势、市场快照和宏观事件等静态数据，因此页面即使显示“数据已更新”，新闻列表仍可能保持不变。

本次新增一套独立的财经新闻聚合与发布流程。产品不以覆盖常规 A 股、港股、美股公司新闻为目标，而是帮助用户及时了解全球正在发生、且可能通过经济机制影响市场或普通人的事件，包括政策、经济数据、央行、贸易、监管、产业供需、公司经营和地缘风险。

成功标准：

- 首页主新闻流只展示最近 24 小时内容。
- 正常情况下收录约 30–60 条可靠新闻；可靠来源不足时按实际数量展示，不以弱相关内容凑数。
- 24–72 小时内仍在持续传导的重大事件进入独立区域，最多 6 条，不混入“最新新闻”。
- 所有公开新闻均可追溯到官方、主流媒体或知名机构的原始页面。
- 新闻具有多轴属性，可进入真实详情页，并为专业解读和「所以呢？」提供结构化输入。
- 页面不再依赖固定演示新闻作为日常新闻源。

## 2. 范围与非目标

### 2.1 本期范围

- 白名单新闻源的定时抓取、规范化、校验、去重和排序。
- 英文内容的中文标题与摘要生成，并保留英文原标题和原文链接。
- 分析层级、事件类型、影响渠道和地区四组多标签分类。
- 24 小时主新闻流和 24–72 小时「持续影响」区域。
- 首页筛选、更新状态、动态新闻详情页及移动端适配。
- 为高重要性新闻生成或承接专业解读与「所以呢？」结构化内容。
- 数据失败降级、质量检查和自动化测试。

### 2.2 非目标

- 不追求覆盖每一家上市公司的日常公告或股价异动。
- 不引入新闻小游戏、答题、积分或娱乐化交互。
- 不复制媒体全文，不绕过付费墙。
- 不把模型生成内容当作事实来源。
- 不因目标数量不足而纳入低可信、弱相关或无法追溯的新闻。
- 不在本期大范围重写与新闻流无关的页面和视觉系统。

## 3. 总体架构

系统继续使用 GitHub Pages 静态部署，不增加常驻后端。GitHub Actions 每小时运行一次新闻任务，输出版本化静态快照 `public/data/news-feed.json`。

数据流：

```text
来源白名单
→ 抓取与字段规范化
→ URL、来源和时间校验
→ 同事件聚类与去重
→ 中文标题 / 摘要生成
→ 多轴分类与因果信号提取
→ 重要性和持续性评分
→ 24 小时主流 / 24–72 小时持续影响
→ news-feed.json
→ 首页与新闻详情页
```

新闻任务与现有市场、宏观数据任务共享更新状态的展示方式，但状态彼此独立。某个新闻源失败不会阻止其他来源生成快照；只有输出文件整体不可用时才回退至上一份成功快照。

## 4. 来源策略与验证

### 4.1 来源等级

来源注册表维护名称、官方域名、类型、地区、抓取方式、启用状态和健康状态。候选来源必须在实施前逐项验证其当前公开接口、使用条件和页面结构。

来源分为三级：

1. `official`：央行、统计部门、财政和监管机构、交易所、政府部门及国际组织的原始发布。
2. `verified`：能确认发布主体、发布时间和永久原文链接的主流媒体或知名研究机构。
3. `cross-checked`：同一事件获得至少两个独立可靠来源确认；这是新闻记录的增强状态，不是新的来源类型。

无法确认发布主体、时间、原始链接或内容归属的来源标记为 `unverified`，不得进入公开新闻流。

### 4.2 验证规则

- 官方发布优先作为同事件的主记录。
- 主流媒体和机构只保存允许使用的元数据、短摘要和原文链接，不保存受版权保护的全文。
- 发布时间必须来自原始发布信息；抓取时间单独记录，不能替代发布时间。
- 重定向后的最终域名必须仍属于白名单或明确允许的官方内容域名。
- 连续抓取异常、返回内容结构失真或无法验证时间的来源自动降级或停用，并在更新状态中记录。

## 5. 新闻数据模型

每条规范化新闻至少包含：

```text
id
canonicalUrl
sourceName
sourceTier
verificationStatus
publishedAt
fetchedAt
originalLanguage
originalTitle
originalSummary
titleZh
summaryZh
translationStatus
analysisLevels[]
eventTypes[]
impactChannels[]
regions[]
keyTerms[]
causalSignals[]
importanceScore
continuingImpactScore
clusterId
relatedSources[]
detailStatus
```

`originalSummary` 只在来源许可且能稳定取得时保存。`detailStatus` 区分普通快讯、可生成专业解读和已具备完整「所以呢？」内容的新闻，避免所有新闻强行填充八个模块。

## 6. 分类、评分与去重

### 6.1 多轴分类

一条新闻可拥有多个互不排斥的属性：

- 分析层级：宏观、行业、公司。
- 事件类型：货币政策、财政政策、监管、贸易、经济数据、公司经营、地缘风险。
- 影响渠道：利率、通胀、汇率、供需、盈利、估值、就业。
- 地区：中国、美国、欧洲、全球，以及 A 股相关、港股相关、美股相关。

分类不能只看关键词。系统结合事件主体、地区、主题、术语、事件类型和因果信号判断。例如，新闻只有在存在“通胀变化 → 利率预期 → 房贷或房地产”的实际传导证据时，才产生住房相关影响；正文偶然出现“住房”不构成充分条件。

分类结果需要保留规则或模型产生的理由信号，以便测试和后续修正。

### 6.2 重要性排序

首页排序综合以下因素：

```text
来源可信度
+ 经济影响范围
+ 事件重要性
+ 发布时间新鲜度
+ 多来源确认度
+ 相对市场预期的偏差
```

官方政策、央行决定、关键经济数据和跨市场事件获得较高基础权重。单家公司新闻只有在显著影响产业链、资本开支、就业、供需或宏观预期时才提高权重。夸张标题但缺乏新增事实的报道降低权重。

### 6.3 同事件去重

系统使用规范 URL、标题相似度、主体、时间窗口、关键数字和事件类型聚类。一个事件在首页只占一条记录：

- 官方来源存在时，官方内容作为主来源。
- 没有官方来源时，选择信息最完整且可信度最高的来源。
- 其他可靠报道列入 `relatedSources`，用于交叉验证。
- 后续报道只有提供实质性新事实、政策变化或数据修正时才拆分为新记录。

## 7. 时间窗口与持续影响

### 7.1 最近 24 小时

主新闻流依据 `publishedAt` 使用滚动 24 小时窗口，而不是按自然日截断。正常目标为 30–60 条。首页「正在发生」从中选出最重要的 5–8 条，其余进入「全部新闻」。

### 7.2 24–72 小时持续影响

该区域最多 6 条，与最新新闻分开。新闻同时满足以下条件才可进入：

- 发布已超过 24 小时但不超过 72 小时；
- 政策尚未落地、事件仍在发展、关键数据仍在传导，或市场预期仍有明显调整；
- 存在新的可靠来源、后续节点或明确的持续性信号。

单纯点击量高、标题热门或昨日重要但已无新增影响，不能进入该区域。达到 72 小时或持续性评分跌破阈值后自动退出。

## 8. 中文生成与事实边界

英文新闻保留英文原标题、来源和原文链接，中文标题与摘要标记为「中文整理」。生成规则：

- 标题忠实表达事实，不添加情绪和交易结论。
- 摘要明确区分事实、机构表态、市场预期和系统推断。
- 数字、单位、机构、人物和时间须与原文一致。
- 不生成“必涨”“必跌”或直接投资建议。
- 内容指纹相同的新闻复用缓存结果，避免每小时重复调用服务。

翻译和摘要服务通过 GitHub Secret 配置，不把密钥写入仓库或前端资源。失败顺序为：

```text
使用同内容指纹的上次成功中文结果
→ 无缓存时展示英文原文
→ 标记生成失败
```

系统不得用词典拼接或未经验证的猜测补造中文内容。

## 9. 页面信息架构

### 9.1 首页

首页按以下顺序展示：

1. 「正在发生」：最近 24 小时最高优先级的 5–8 条。
2. 「全部新闻」：最近 24 小时的完整新闻流，支持按地区、分析层级和事件类型筛选。
3. 「持续影响」：24–72 小时内仍在传导的重大事件，最多 6 条。

卡片默认显示中文标题、短摘要、原始发布时间、来源和 3–5 个最有信息量的属性。更多标签及验证信息进入详情页，避免卡片信息过载。

### 9.2 新闻详情页

动态新闻使用真实 ID 路由读取快照数据，不再只通过 `demoData.ts` 查找固定记录。详情页展示：

- 新闻事实、关键数据及原始来源；
- 中文整理标记和英文原标题；
- 多轴新闻属性；
- 专业摘要；
- 交叉验证来源；
- 已识别的关键术语和因果信号；
- 在内容充分时展示专业解读及「所以呢？」。

普通快讯可以只显示可靠事实和专业摘要。完整「所以呢？」只用于信息充分且重要性达到阈值的新闻，避免空泛生成。

### 9.3 移动端

- 沿用现有字体、玻璃卡片、颜色和响应式系统。
- 卡片减少次要元数据，保留标题、摘要、时间、来源和关键标签。
- 标签可横向滚动或折叠，不能挤压标题区域。
- 筛选器收进简洁抽屉，并提供清除状态。
- 详情页「所以呢？」继续渐进展开，不一次铺满全部模块。
- 交互目标尺寸和文本行高满足触屏阅读需要。

## 10. 更新状态与错误处理

首页显示：最近成功更新时间、下一次预计更新时间、24 小时新闻数量及数据状态。

数据状态包括：

- 正常：最近一次任务成功，核心来源可用。
- 部分来源异常：快照成功，但一个或多个来源失败或停用。
- 更新延迟：超过两小时没有成功生成新快照。

失败策略：

- 单个来源失败时继续处理其他来源，并记录来源错误。
- 整体生成失败时保留上一份成功快照，不写入半成品。
- 页面读取失败时显示更新时间与错误提示，可重新加载。
- 不以演示新闻静默补位，也不把旧快照标成最新数据。
- 动态新闻链接在合理保留期内仍可访问；归档策略在实施计划中以静态历史索引实现，不要求常驻数据库。

## 11. 组件与职责边界

实施时保持单一职责，预计包含以下逻辑边界：

- 来源注册表：维护白名单、来源元数据和抓取适配器配置。
- 抓取适配器：把不同来源转换为统一的原始新闻记录。
- 验证器：检查域名、时间、链接和必需字段。
- 聚类器：合并同一事件并管理交叉验证来源。
- 分类器：生成多轴标签、关键术语和因果信号。
- 排序器：计算重要性、新鲜度和持续影响评分。
- 中文生成器：翻译、摘要、缓存和失败降级。
- 快照发布器：原子写入新闻流、状态和必要的历史索引。
- 前端数据层：加载、验证和查询动态新闻。
- 新闻流 UI：展示区域、筛选器、状态和移动端布局。
- 详情页适配层：把动态数据映射到专业解读和「所以呢？」组件。

不把所有逻辑堆入单个脚本或页面组件；各边界应能使用固定输入独立测试。

## 12. 测试与发布验证

自动测试至少覆盖：

- 滚动 24 小时窗口、24–72 小时窗口及时区边界。
- 白名单准入、官方来源优先和非白名单排除。
- URL、发布时间和必要字段验证。
- 同事件聚类、官方主来源选择和实质性更新拆分。
- 多轴分类以及基于传导关系而非单纯关键词的判断。
- 翻译缓存、数字保护、失败回退和英文原文展示。
- 部分来源失败、整体失败和旧快照降级。
- 动态新闻详情路由和历史链接。
- 首页区域、筛选器、新闻数量和移动端关键交互。
- 「所以呢？」面对缺失可选字段时的安全降级。

发布前运行现有测试、类型检查和生产构建。部署后验证：

- GitHub Actions 确实生成新的新闻快照和状态。
- GitHub Pages 加载的文件版本与最近成功任务一致。
- 首页数量、时间和来源与快照一致。
- 抽查官方、主流媒体和知名机构三类记录的原始链接。
- 桌面与移动视口均能打开动态详情页并正确筛选。

## 13. 实施约束与顺序

- 开始实现前先验证候选来源当前可用的官方接口、RSS 或公开页面，形成明确白名单；未验证来源不得进入生产配置。
- 第一阶段优先打通可靠数据流、24 小时窗口、去重、分类和首页动态展示。
- 第二阶段接入动态详情页、中文生成和高重要性新闻的深度解读。
- 所有更改复用现有组件、字体、玻璃卡片和响应式规则，不扩展到无关页面重构。
- 具体文件拆分、迁移步骤和测试顺序由后续实施计划确定。
